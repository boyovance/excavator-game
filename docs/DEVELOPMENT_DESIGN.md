# 開發設計文檔

版本：0.1；日期：2026-10-16；對應 [項目計劃書](PROJECT_PLAN.md)。

「現有」表示已存在的實現；「M0」表示本輪工程修復；「M1 提案」尚未變更遊戲行為，需使用者確認。

## 1. 架構與資料流（現有）

```text
桌面場景 Phaser / 車庫 DOM
    → preload API（無 Node 權限）
    → Electron IPC（主進程持有 token）
    → 本機 HTTP /dispatch
    → 驗證、冷卻、時間／亂數 → shared reducer → 新狀態
    → JSON 寫入（延遲、重試、備份）
    → SSE /events → 主進程 → IPC state → 場景／車庫
```

頁面負責輸入、動畫和呈現；主進程負責視窗、檔案對話框、托盤及權限；本機服務負責經濟與進度的單一狀態。`src/shared/reducer.mjs` 接收明確 action，`rewards.mjs` 計算獎勵，`normalize.mjs` 處理舊存檔和未知資料。

網頁模式是 localStorage mock，用於介面開發；它不完整模擬服務端冷卻和持久化，正式規則以桌面服務為準。本機 token 旨在限制其他網頁存取，不是對本機擁有者的防作弊機制。

## 2. 模組責任

| 模組 | 責任 | 修改原則 |
| --- | --- | --- |
| electron/main、windows、ipc、preload | 啟動、視窗、安全與頁面橋接 | 不在此計算金幣、掉落或升級 |
| server/index.mjs | HTTP/SSE、驗證、冷卻、權威狀態 | 客戶端不提供獎勵數字或可信時間 |
| server/persistence.cjs（M0） | 原子替換、有效備份、延遲寫入及重試 | 不依賴 Electron，可用臨時目錄測試 |
| src/shared/reducer、rewards、normalize | 遊戲規則與遷移 | 每個規則變更有邊界案例 |
| src/shared/data | 機型、配件、工地、繪圖資料 | 屬於源碼，必須進 Git |
| ExcavatorScene、scene/* | 場景狀態機和效果 | 動畫不直接改持久化狀態 |
| garage/* | 車庫各功能區及預覽 | 派遣／購買呼叫 API，由狀態回傳更新畫面 |
| skins/*、electron/content | 內建／簽名外觀包 | 圖片外觀與遊戲獎勵規則分離 |

## 3. 現有資料與規則

`GameState` 包含 name、mood、moodAt、since、together、lastDay、milestone、xp、coins、durability、owned、equipped、loadouts、tint、job、report。完整型別以 `src/shared/reducer.d.mts` 為準。

目前 job 為 `{ site, start, end }`；report 記錄工地、金幣、掉落、是否大豐收、時間及是否看過。派遣到時後由場景發送 claim；`tick` 本身不結算。關閉程式不累積多輪派遣，重開後僅可結算原先的一次。

現有公式：

- 挖掘金幣：`max(1, round(4 × 裝備 coin 乘積))`，一次挖掘耐久 -3、經驗 +2。
- 維修價格：`ceil((100 - durability) × 0.3)`。
- 等級：`1 + floor(sqrt(max(0, xp) / 20))`。
- 派遣：兩次亂數平均決定區間金幣，大豐收可翻倍，再乘 jobCoin；配件重複則折現。現有規則使用結算時裝備，M1 提案改為出發快照。

冷卻、輸入白名單與服務時間集中在 server；新功能不可繞過此路徑。

## 4. M0 持久化與安全

### 持久化

一般進度先更新記憶體，約 300ms 內合併寫入。寫失敗記錄日誌、保持待寫入的最新狀態，約 2 秒後重試。設定與進度共用寫入器；退出時立即 flush，仍失敗時顯示提示。

寫入順序：新 JSON → 同目錄 `.tmp` 並 flush → 如舊 JSON 有效，原子更新 `.bak.json` → rename 新 JSON。損壞的主檔不覆蓋已知有效備份。這保障常見寫入失敗下的恢復，並非斷電／硬體損壞的完整備援方案。

匯入／重置先由主進程寫備份，再呼叫服務；候選狀態成功落盤後才替換記憶體和廣播。備份失敗中止操作，服務寫失敗回傳 503，保留原狀態。網頁得到的成功提示必須對應已完成持久化。

### 安全

BrowserWindow 明確使用 contextIsolation、sandbox、nodeIntegration=false。每個窗口載入前登記允許的完整頁面 URL；IPC 驗證 sender 是該窗口頂層 frame 且 URL 相符，fragment 可變。拒絕外部導航、重定向、新窗口、webview 及權限要求。

CSP 限制腳本來自本地頁面來源，不允許 inline script/eval；圖片允許自有資源、data/blob 及簽名內容協議；樣式保留 inline 兼容，開發 WebSocket 僅允許本機 5173。外觀名稱與顯示器選項用 DOM Option 建立，避免將文字當 HTML。

## 5. M1 派遣閉環提案（待確認）

### 玩家流程與介面

```text
工地卡片：名稱／時長／適用機型／金幣區間／可能掉落／磨損
  → 出發確認：機型、配件加成、預計完成時間
  → 工作中：進度、剩餘時間、召回
  → 已完成：查看收穫
  → 結果：基礎金幣、加成、大豐收、重複折現、新物品
  → 領取成功：收藏與餘額更新，返回可派遣
```

建議先使用既有車庫的派遣區，不另開主視窗。已完成時按鈕明確顯示「領取收穫」；領取中禁用連點，服務仍需保證重複請求不重複支付。離線回來顯示同一個待領取工作。

### 待使用者確認的產品選擇

| 決策 | 建議 | 與目前差異 |
| --- | --- | --- |
| 收穫時機 | 完成後手動領取 | 現在場景自動 claim |
| 派遣數量 | 保留一個工作槽 | 先不增加多機隊管理 |
| 派遣期間換裝 | 車庫可換，但不改正在執行工作的快照 | 現在結算使用當下裝備 |
| 磨損 | 使用出發配置計算，完成領取時套用一次 | 避免換機刷收益；跨機型耐久需進一步定義 |
| 召回 | 未完成可召回且無收穫；已完成只能領取 | 防止誤丟已完成獎勵 |

其中「各機型共用耐久或獨立耐久」會影響範圍：M1 建議先維持現有共用耐久，在確認文案中說明；獨立耐久放後續機庫設計。

### 資料與實現提案

在 job 增加 `id`、`machineId`、`equippedSnapshot`、`rulesVersion`；以 start/end 推導 running/completed，避免持久化兩個不同步的狀態。report 增加 jobId 與獎勵明細，方便驗收及顯示。

開始工作由服務生成 id 和快照；收益和掉落適配只讀快照；完成後 claim 在單一服務事件循環中結算並清空 job。相同工作再次 claim 返回原結果或無變更，不能再次加金幣。

M1 需為領取設計持久化確認：持久化成功後才廣播成功，失敗保留待領取狀態。獎勵亂數應在開始／完成時固定並保存，避免磁碟寫入失敗時重新抽取；不得在每次重試時重抽。

舊 job 沒有快照時，正規化遷移從存檔當前裝備生成一次快照，保持 start/end 和已有進度；記錄版本，不使用反覆讀取時重新生成的隨機 id。實現前補上存檔 schemaVersion 的具體遷移表。

### 變更區域與拆分

- server：開始／領取 action 的驗證、固定亂數、持久化成功回應。
- shared：job 型別、normalize 遷移、快照收益計算與明細。
- garage/jobs：工地卡片、出發確認、領取與結果區。
- scene：將派遣的離開、工作、返回和領取協調拆成獨立控制器；`ExcavatorScene` 保留通用移動、拖曳、碰撞與動畫驅動。
- preload/API：需要確認的操作以 Promise 回傳結果；不能以「發送訊息成功」視為「領取成功」。

拆分與具體功能一起進行，先補行為測試再移動程式，避免單純追求行數減少。

### M1 驗收案例

1. 有效機型可派遣，不適用機型顯示原因且服務拒絕請求。
2. 出發後更換機型／配件，結算仍採用出發配置。
3. 提前領取無獎勵；到時後領取一次成功，連點／重試均不重複給獎。
4. 工作中退出並重啟，倒數與工地保留；離線超時只產生一次收穫。
5. 召回規則與提示一致；已完成收穫不被意外召回抹除。
6. 重複配件明確顯示折現，新配件能在 M2 圖鑑追蹤。
7. 存檔失敗不顯示成功，恢復後領取結果不重抽。
8. 舊存檔可讀，已有金幣、配件、派遣進度保留。

驗收用例可注入時鐘與固定 rolls 縮短測試，不改正式工地時間。

## 6. M2～M4 設計約束

M2：圖鑑資料從 PARTS/SITES 推導，不複製第二套來源。區分未擁有、可購買、派遣限定及不適配；比較只顯示實際影響的 coin/jobCoin/speed 等數值。

M3：等級／解鎖／里程碑用服務規則判定，介面只呈現；新增獎勵需永久已領標記與遷移。暫不預設材料種類或技能樹。

M4：新增離線平衡模擬腳本，固定種子輸出可重現報告；分析不同裝備、收藏階段、重複折現及維修淨收益。數值變更經體驗確認再落地。

這三區的詳細畫面與資料結構在上一區驗收後補充，避免把未確認想法誤當開發指令。

## 7. 開發、測試與交付

每區使用一個具體目標及可追蹤提交。依序：更新本文件 → 實現 → 針對規則／存檔邊界測試 → build → 有桌面改動則 smoke → 交付驗收 → 記錄反饋。

CI 對乾淨 checkout 執行 npm ci、測試、建置及依賴掃描；Windows 額外跑 Electron 冒煙與目錄打包。安裝包不進 Git。Windows 安裝、升級、退出與多螢幕手感仍需人工驗收。

發布前保存可回退提交與測試記錄。不得為修復測試而重置使用者真實存檔；測試必須使用臨時資料夾。升級需保持原始錯誤日誌、無敏感 token 的診斷與備份可用。
