版本：0.7；日期：2026-10-17；對應 [項目計劃書](PROJECT_PLAN.md)。

M0 為工程基礎；M1～M4 已獲使用者確認；M4 方案 A 已接入 0.8.0 新派遣。M5 本機驗證與封裝資源驗證已交付，乾淨系統及人工項未驗收。本輪不新增美術。M1～M4 各首輪記錄反映當時設計，現行規則以 6.2／6.3 為準。

## 1. 架構與資料流（現有）

```text
桌面場景 Phaser / 車庫 DOM
    → preload API（無 Node 權限）
    → Electron IPC（主進程持有 token）
    → 本機 HTTP /dispatch
    → 驗證、冷卻、時間／亂數 → shared reducer → 新狀態
    → JSON 寫入（普通操作延遲；派遣轉換先持久化成功）
    → SSE /events → 主進程 → IPC state → 場景／車庫
```

頁面負責輸入、動畫和呈現；主進程負責視窗、檔案對話框、托盤及權限；本機服務負責經濟與進度的單一狀態。`src/shared/reducer.mjs` 接收明確 action，`rewards.mjs` 計算獎勵，`normalize.mjs` 處理舊存檔和未知資料。

網頁模式是 localStorage mock，用於介面開發；它不完整模擬服務端冷卻和持久化，正式規則以桌面服務為準。本機 token 旨在限制其他網頁存取，不是對本機擁有者的防作弊機制。

## 2. 模組責任

| 模組 | 責任 | 修改原則 |
| --- | --- | --- |
| electron/main、windows、ipc、preload | 啟動、視窗、安全與頁面橋接 | 不在此計算金幣、掉落或升級 |
| server/index.mjs | HTTP/SSE、驗證、冷卻、權威狀態 | 客戶端不提供獎勵數字或可信時間 |

## 3. 現有資料與規則

`GameState` 包含 name、mood、moodAt、since、together、lastDay、milestone、xp、coins、durability、owned、equipped、loadouts、tint、job、report。完整型別以 `src/shared/reducer.d.mts` 為準。

job 現為 `{ id, site, start, end, machineId, equippedSnapshot, rulesVersion, rolls }`；report 增加 jobId、machineId 和 breakdown。派遣到時只呈現待領取，車庫發送帶 jobId 的 claim；場景和 `tick` 都不結算。關閉程式不累積多輪派遣，重開後僅可領取原先的一次。

現有公式：

- 挖掘金幣：`max(1, round(4 × 裝備 coin 乘積))`，一次挖掘耐久 -3、經驗 +2。
- 維修價格：`ceil((100 - durability) × 0.3)`。
- 等級：`1 + floor(sqrt(max(0, xp) / 20))`。
- 派遣：兩次亂數平均決定區間金幣，大豐收可翻倍，再乘出發快照的 jobCoin；配件重複則折現。掉落適配使用出發機型，重複判斷使用領取時收藏。

冷卻、輸入白名單與服務時間集中在 server；新功能不可繞過此路徑。

## 4. M0 持久化與安全

### 持久化

一般進度先更新記憶體，約 300ms 內合併寫入。寫失敗記錄日誌、保持待寫入的最新狀態，約 2 秒後重試。設定與進度共用寫入器；退出時立即 flush，仍失敗時顯示提示。

寫入順序：新 JSON → 同目錄 `.tmp` 並 flush → 如舊 JSON 有效，原子更新 `.bak.json` → rename 新 JSON。損壞的主檔不覆蓋已知有效備份。這保障常見寫入失敗下的恢復，並非斷電／硬體損壞的完整備援方案。

匯入／重置先由主進程寫備份，再呼叫服務；候選狀態成功落盤後才替換記憶體和廣播。備份失敗中止操作，服務寫失敗回傳 503，保留原狀態。網頁得到的成功提示必須對應已完成持久化。

### 安全

BrowserWindow 明確使用 contextIsolation、sandbox、nodeIntegration=false。每個窗口載入前登記允許的完整頁面 URL；IPC 驗證 sender 是該窗口頂層 frame 且 URL 相符，fragment 可變。拒絕外部導航、重定向、新窗口、webview 及權限要求。

CSP 限制腳本來自本地頁面來源，不允許 inline script/eval；圖片允許自有資源、data/blob 及簽名內容協議；樣式保留 inline 兼容，開發 WebSocket 僅允許本機 5173。外觀名稱與顯示器選項用 DOM Option 建立，避免將文字當 HTML。

## 5. M1 派遣閉環（使用者已驗收）

### 玩家流程與介面

```text
工地卡片：名稱／時長／適用機型／金幣區間／可能掉落／磨損
  → 出發確認：機型、配件加成、預計完成時間
  → 工作中：進度、剩餘時間、召回
  → 已完成：待領取（不自動加錢）
  → 領取收穫：持久化成功後收藏與餘額更新
  → 結果：基礎金幣、加成、大豐收、重複折現、新物品；返回可派遣
```

使用既有車庫的派遣區，不另開主視窗。已完成時按鈕明確顯示「領取收穫」；請求中禁用連點，服務另有 jobId 冪等檢查。離線回來顯示同一個待領取工作。

### 本次採用的產品選擇

| 決策 | M1 實現 | 與 M0 差異 |
| --- | --- | --- |
| 收穫時機 | 完成後手動領取 | M0 場景自動 claim |
| 派遣數量 | 保留一個工作槽 | 先不增加多機隊管理 |
| 派遣期間換裝 | 車庫可換，但不改正在執行工作的快照 | M0 結算使用當下裝備 |
| 磨損 | 依工地既有磨損，領取時套用共用耐久一次 | 現有裝備無磨損倍率，不新增機型獨立耐久 |
| 召回 | 未完成可召回且無收穫；已完成只能領取 | 防止誤丟已完成獎勵 |

其中「各機型共用耐久或獨立耐久」會影響範圍：M1 建議先維持現有共用耐久，在確認文案中說明；獨立耐久放後續機庫設計。

### 資料與實現

job 增加 `id`、`machineId`、`equippedSnapshot`、`rulesVersion: 1`、11 個固定 `rolls`；以 start/end 推導 running/completed，避免持久化兩個不同步的狀態。report 增加 jobId、machineId 與 breakdown（base、jackpotBonus、equipmentBonus、duplicates、xp、wear）；drop 增加重複折現的 coins。

開始工作由服務生成 UUID 和快照；收益和掉落適配只讀快照；完成後 claim 在單一服務事件循環中結算並清空 job。HTTP claim／cancelJob 必須帶 jobId；最近一份報告的重複 claim 回傳成功及目前狀態但不支付。舊工作請求不會領取新工作；超出最近報告的舊 ID 回傳衝突，不保存無限歷史。

開始、召回、領取皆呼叫同步原子 commit，成功後才替換記憶體／廣播。503 表示存檔失敗，409 表示狀態衝突，400 表示非法請求；介面不在失敗時顯示成功。亂數在開始時保存；重試只讀原 rolls。網路超時不等於未結算，提示無法確認並允許同 ID 重試。

舊 job 沒有快照時，正規化遷移從存檔當前裝備生成一次快照，保持 start/end 和已有進度。由工地、開始及結束時間產生穩定 legacy ID，再由 ID 產生固定 rolls；重讀／重試不重抽。無法還原舊版本原本未保存的出發配置。

| 輸入版本 | 遷移 |
| --- | --- |
| 無 schemaVersion／1 | 保留金幣、收藏及進度；job 補快照、ID、規則版本與固定 rolls；輸出 schemaVersion 2 |
| schemaVersion 2 | 驗證並複製有效 job 資料；不重抽 rolls，不讀當前裝備覆蓋既有快照 |
| 舊 report | 保留原有總收益及掉落；無明細不偽造，未記錄折現數字只顯示已折現 |

`rulesVersion` 本輪僅使用 1；尚無跨數值版本獎勵路由，M4 改數值前須補版本策略。本機時間回撥與直接修改存檔不是防作弊保障範圍。

### 變更區域與拆分

- server：開始／領取 action 的驗證、固定亂數、持久化成功回應。
- shared：job 型別、normalize 遷移、快照收益計算與明細。
- garage/jobs：工地卡片、出發確認、領取與結果區。
- scene/jobs：派遣離開、工作、返回與等待協調；沒有結算權限。`ExcavatorScene` 保留通用移動、拖曳、碰撞與動畫驅動，派遣期間以出發快照繪製機型及配件，車庫預覽仍反映目前換裝。
- preload/API：需要確認的操作以 Promise 回傳結果；不能以「發送訊息成功」視為「領取成功」。

拆分與具體功能一起進行，先補行為測試再移動程式，避免單純追求行數減少。

### M1 驗收案例

1. 有效機型可派遣，不適用機型顯示原因且服務拒絕請求。
2. 出發後更換機型／配件，結算仍採用出發配置。
3. 提前領取無獎勵；到時後領取一次成功，連點／重試均不重複給獎。
4. 工作中退出並重啟，倒數與工地保留；離線超時只產生一次收穫。
5. 召回規則與提示一致；已完成收穫不被意外召回抹除。
6. 重複配件明確顯示折現，新配件能在 M2 圖鑑追蹤。
7. 存檔失敗不顯示成功，恢復後領取結果不重抽。
8. 舊存檔可讀，已有金幣、配件、派遣進度保留。

驗收用例可注入時鐘與固定 rolls 縮短測試，不改正式工地時間。

自動檢查：`tests/jobs.test.mjs` 驗證規則、遷移、存檔失敗與重啟；`npm run test:dispatch` 在獨立 Electron 存檔跑完整畫面流程及截圖。`npm run demo:dispatch` 同樣驗證後保留演示視窗供使用者領取，不改正式進度。畫面驗收前，不進入 M2。

## 6. M2 零件圖鑑與搭配（使用者已驗收）

本次範圍：擴充既有零件倉庫，不新增獨立視窗、配方、材料、稀有度、技能或數值調整。不新增存檔欄位，收藏仍以 owned 為準，機型搭配沿用 loadouts。

### 玩家流程

車庫「零件圖鑑與搭配」 → 類別／搜尋／收藏狀態／目前機型適配篩選 → 查看零件 → 並排比較目前與試裝外觀、實際收益差異及來源 → 購買並裝備／裝備已有零件，或前往來源工地查看。查看／試裝本身不花錢、不保存、不開工，關閉恢復原配置。

### 介面與資料規則

- 圖鑑顯示全收藏與當前分類的進度，分類保留機型、配件、駕駛員和自訂顏色；不相容物品不再直接隱藏，可勾選只看適配。
- 狀態區分已裝備、已擁有、未擁有；另標可購買、派遣限定、初始配件／機型附送，並顯示不適配原因。搜尋名稱與描述，篩選不修改存檔。
- 來源由 PARTS、SITES、machine.defaults 和 machineDrop.pool 推導。列出商店價格、初始取得、隨機型附送、可能掉落工地；工地另標目前機型是否能進入並取得，不把進入工地等同必定掉落。
- 未擁有或不適配仍可查資料；不適配零件不套到錯誤機型，不可購買／裝備，列出適用機型。
- 機型試裝使用正式 switchMachine/loadoutFor 相同規則：已有機型恢復記住的配置，未有機型使用標配；不可全部一律重設標配。比較與 2D 繪圖共用同一候選配置。
- 比較只顯示實際的單次挖掘金幣、派遣收益倍率、行走速度倍率（含目前耐久影響）。純外觀零件明確提示沒有數值變化，不捏造戰力／稀有度。圖片整張外觀不支援換件時明確提示。
- 購買按鈕明確寫「購買並裝備」，餘額不足／派遣限定／不適配禁止操作。購買及裝備增加 Promise 確認與先持久化後成功，連點不重複扣款，失敗保留原配置和金幣；不新增收費或改價格。
- 派遣中可調整車庫配置，但提示不影響進行中的出發快照。來源跳轉只導覽，不自動派遣。

### M2 驗收與實現拆分

shared/catalog：純函式來源索引、篩選、候選配置和差異，與 reducer 一致性測試；garage/parts：搜尋、卡片、詳情與操作；garage/preview：共用候選配置的兩幅 2D 畫面；server/IPC/API：購買／裝備確認；獨立 Electron 測試／演示使用臨時存檔。

驗收：收藏進度與 owned 一致；搜尋空結果有提示；所有來源可追溯；機型不適配有原因且不能強裝；試裝不扣錢；已有機型恢復搭配；比較與真正裝備一致；購買僅扣一次；存檔失敗不顯示成功；派遣快照不受換裝影響；普通／窄視窗、長描述、鍵盤關閉及頁面重載正常。完成後提供真實截圖與演示，等待使用者確認再進入 M3。

本機驗證已完成：`tests/catalog.test.mjs` 對照所有可購買／已擁有適配物品的 reducer 結果、來源及服務持久化；`npm run test:catalog` 在獨立 Electron 存檔測試完整畫面。`npm run demo:catalog` 留下可操作的試裝視窗。購買重試若物品已擁有則回傳衝突，不再扣款；重新連線後以收藏狀態確認結果。

## 6.1 M3 成長與解鎖

### 本輪規則（首版，交付後驗收節奏）

保留既有經驗來源與等級公式，不限制零件購買，不加入技能樹或材料。升級自動開放工地；領取升級獎勵不是開放工地的前置條件。等級開放與機型適配是兩個獨立條件，仍需正確機型及耐久才能出發。

| 等級 | 累計經驗 | 開放工地 | 一次性金幣獎勵 |
| --- | --- | --- | --- |
| 1 | 0 | 廢料場 | 無 |
| 2 | 20 | 窄巷管線 | 20 |
| 3 | 80 | 採石場、廢鋼場 | 30 |
| 4 | 180 | 河道清淤、鐵路養護 | 40 |
| 5 | 320 | 山坡施工 | 50 |
| 6 | 500 | 深層礦坑 | 60 |

Lv.6 完成這一版工地路線後仍可累積經驗升級，明確提示目前路線完成，不能顯示不存在的下一工地。獎勵是本輪新增的階段回饋，現有工地收入、價格、維修及掉落數據不變；完整經濟調整留到 M4。

### 資料與交易

- `shared/growth` 集中保存等級門檻、階段獎勵與工地權限判定；server/reducer、派遣畫面與圖鑑來源共用。
- schemaVersion 升為 3，新增 `growthClaimed: string[]`（永久已領 ID）、`legacySites: string[]`（舊存檔保留權限）。新遊戲兩者為空。
- 非空的版本 1／2 舊存檔保留當時所有既有工地的權限，以明確 ID 保存，未來新增工地不自動豁免。仍檢查機型適配；已有收藏、配置、金幣、經驗、派遣快照與領取狀態保留。遷移不自動給升級獎勵，已達標者可各領一次。
- `claimGrowth { id }` 僅接收規則 ID，服務根據持有經驗判定並計算金額；不信任客戶端 level/coins/xp。獎勵與已領標記一起原子寫入後才成功，重試已領 ID 回傳成功但不再加錢。存檔失敗不標記、不入帳，可重試。
- 舊存檔保留權限不代表達成等級獎勵；不可用它提前領取。既有派遣的領取不因新增等級限制失效。

### 畫面與驗收

車庫快捷入口 → 成長面板（等級、經驗條、下一級差額、下一批解鎖）→ 路線卡片（工地、機型要求、未達成／可領取／已領取）→ 手動領取與持久化回饋。舊存檔顯示保留權限提示。派遣卡片及零件來源同步顯示等級門檻，避免圖鑑說可前往但派遣拒絕。

### M3 驗收調整：派遣升級整合結果（使用者已授權）

- 問題：派遣區領取後，升級與待領獎勵在成長區，玩家需自行跳轉才能看到，回饋不連貫。
- 手動領取派遣成功且本次經驗造成升級時，自動展示一張整合結果卡：派遣收穫已入庫、等級前後、新開放工地與機型要求、這次達成的階段獎勵。結果卡中可直接領取階段獎勵，成功／失敗都在同卡回饋，不再彈第二層視窗。
- 未升級不彈窗，保持原派遣結果並捲動到結果位置。一次跨多級集中在同卡，各階段仍各領一次。Lv.6 以後只展示實際升級，不捏造新工地或獎勵；舊玩家保留的工地不誤標為首次開放。
- 可以「稍後領取」或 Escape 關閉；成長面板與入口保留待領提醒。狀態推送、重複回應、重新開啟車庫均不再次自動彈出已看結果。桌面挖掘／互動升級沿用輕量提示，不主動打開車庫。
- 只有領取成功後呈現已入庫；階段獎勵共用既有 claimGrowth 交易與防連點，儲存中禁止關閉，失敗原地重試。階段獎勵與派遣收益分區，不把同一筆錢算兩次。不變更數值或存檔版本。
- 回歸新增：無升級不彈、成功自動展示、失敗不誤彈、原地領獎與失敗重試、跨多級、稍後領取／Escape、重載不再彈、窄視窗／暗色。演示從已完成派遣開始，按一次「領取收穫」即可看到整合卡。

驗收案例：門檻前後、一次跨多級、未達標／未知／偽造請求、連點重試、存檔失敗恢復、服務重啟、舊存檔與派遣兼容、圖鑑來源一致、窄視窗／暗色、等級路線完成。獨立演示提供接近升級的待領派遣，玩家領收穫後可看到升級、工地開放及領取階段獎勵。正式存檔不參與測試。

## 6.2 M4 經濟平衡：測量與候選試玩

### 邊界與目標

先量測原版，再用固定種子比較候選 A；不把暫定數字套進正式遊戲。目標（待體驗確認）：標準機標配維修後約 230～310 金幣／派遣小時；新玩家僅派遣、及時領取、維修並領階段獎勵時，首台 150 金幣微型機中位時間約 20～35 分鐘。這些是模型目標，不是對實際遊玩時間的保證。

長工地以單趟收入和少操作為優勢，短工地以每小時零件機會及更頻繁回饋為優勢；同機型比較金幣、經驗、零件、新機型概率與操作頻率，另外保留工地獨有來源，不把一個收益數字當作唯一評價。

### 方案 A（2026-10-17 確認，0.8.0 套用新派遣）

- 保留工地時間、機型／等級限制、掉落表、機型掉落率、商店價格、裝備倍率、升級獎勵與維修單價。避免一次改太多無法判斷原因。
- 每趟金幣範圍：廢料場 12～32、窄巷 42～78、採石 85～155、廢鋼 80～160、河道 150～230、山坡 220～320、鐵路 90～140、礦坑 300～700。採石經驗 75（原 70），和廢鋼的機型收集方向分工；其他經驗不變。
- 重複零件折現改為標價（無標價按 60）的 25%，最低 5、最高 25 金幣。新收藏不折算成現金，不把收藏價值算進淨收入。
- 出發需耐久至少等於該工地磨損；領取最低可到 0，不再靠固定 1 點耐久無限免費派遣。保留現有免費休息恢復作為低資金退路；不自動扣維修費。

### 實現與舊工作兼容

`shared/economy` 集中版本 1（原版）與版本 2（已採用方案 A）的查表。0.8.0 正式 reducer／服務預設使用 CURRENT_ECONOMY_VERSION=2；客戶端 action 不能指定版本。獨立模擬可用第三參數比較版本 1／2。出發將版本記入 job，結算依 job.rulesVersion，不因升級重算舊工作。舊 job 缺版本／未知版本按原版遷移，已保存的合法版本及 rolls 保留；原版收益和耐久下限須回歸不變。資料表 SITES 保留原版內容作兼容，當前出發畫面必須使用 economySites／economySite。

`src/shared/balance.mjs` 共用正式 reducer、結算及維修規則，固定種子；不複製獎勵引擎。`scripts/balance-report.mjs` 輸出 JSON 與可閱讀 HTML 報告到 artifacts/balance。獨立 Electron 試玩頁無 preload、無本機 API、無正式存檔讀寫；可切換原版／候選、機型／搭配／收藏條件，模擬完成派遣、維修、購買微型機及領階段獎勵。加速只跳模擬時間，不改正式工地。

### 模擬口徑與驗收

- 11 機型 × 可進入工地 × 標配／商店最佳派遣倍率／全收藏最佳倍率 × 初始／半數／全收藏，分開比較兩方案。靜態批次每趟從同一收藏快照重置；初始收藏允許同趟第二件變重複，不冒充完整養成歷程。
- 拆出基礎、大豐收、裝備、重複折現、每趟恢復至滿耐久的實付維修費；輸出淨金幣／小時、經驗／小時、新零件／小時、總零件／小時、新機型／小時。時間假設立即領取和接下一趟，不含玩家未回來的空窗。
- 動態新手路線用真正累積收藏、金幣、等級、維修和階段獎勵，輸出首台微型機時間 P50/P90；掉落限定機型首個獲取時間另列 P50/P90，從可進入該工地且機型具備開始計，不含前置解鎖時間。無保底，分位數不是上限。
- 對照每趟維修與不維修策略，揭露原版 1 耐久連派的維修成本偏差；檢查候選不足耐久禁止出發、無負金幣、重複領取不付款、版本切換／舊存檔結算一致。
- 報告列假設、樣本量、種子、支配關係及未達目標項，不宣稱有限抽樣能保證全局平衡。回歸：固定種子重現、拆帳一致、原版不變、候選版本固定、試玩頁重置／隔離、窄視窗與暗色。

### 首輪實測與待確認項

種子 20261016，630 組情境各 3000 趟；新手購買及每個指定掉落機型另各 2000 條累積路線。標準機標配、起始收藏的候選每小時淨幣為 243.8～276.8（原版 218.5～334.1），位於提案區間；兩方案首台可購微型機均為 P50 30 分鐘、P90 35 分鐘。不含桌面挖掘與玩家回訪間隔，不代表真實日曆等待時間。

全收藏標準機標配的候選淨幣為 292.8～326.8／小時。純速率上仍有部分工地被其他工地壓過，報告公開具體配對；尚不能宣稱所有工地等價。礦用機指定掉落 P50 約 18 小時、P90 約 50 小時，尚無保底。需確認維修頻率、長短工地取捨與長尾接受度；本輪不擅自新增保底、變更正式數值或開始 M5。

免費休息試玩用既有 reducer 恢復至 15，以服務接受的最短間隔每點 2.5 秒快轉計時；不是正式桌面動畫速度或實測操作時間。正式接入候選時，須同步更新車庫出發條件、預估收益與耐久提示，再重新驗證存檔與 UI，而不是只切換服務預設版本。

## 6.4 M6 新機型掉落保底（2026-10-22 確認）

使用者確認 M5 本機可做的驗收已完成，發佈先只供自己使用；同意以 M4 遺留的「機型掉落長尾」作為下一功能區。

### 問題（實測）

7 台只能從派遣取得的機型（workOnly，商店不賣）每趟派遣只擲一次機型掉落，沒有保底。以現行掉落表、固定種子各 20000 條路線模擬「連續派遣同一工地直到取得目標機型」的派遣時數：

| 工地（每趟） | 目標 | 單趟機率 | P50 | P90 | 最差 |
| --- | --- | --- | --- | --- | --- |
| 廢料場（5 分） | 超微型 | 3% | 3.2h | 9.0h | 29.5h |
| 窄巷（15 分） | 蜘蛛 | 6% | 6.3h | 16.3h | 62.8h |
| 採石場（30 分） | 拆房 | 7% | 7.0h | 21.0h | 86.0h |
| 廢鋼場（30 分） | 物料搬運 | 8% | 7.0h | 20.0h | 69.5h |
| 河道（45 分） | 水陸兩用 | 10% | 5.3h | 16.5h | 81.0h |
| 山坡（60 分） | 蜘蛛 | 10% | 10.0h | 29.0h | 102.0h |
| 深層礦坑（120 分） | 礦用 | 12%（池中礦用 2／3） | 16.0h | 48.0h | 186.0h |

時數是連續派遣累計，不是日曆時間；桌面寵物玩家一天回來幾次，最差情況可能拖上數週。中位數本身可接受，問題在沒有上限。

### 建議方案：每工地硬保底

- 每個有機型掉落的工地各自記錄「連續未出新機型的次數」。某工地的派遣若沒掉出新機型，該工地計數 +1；掉出時歸零。切換工地不會清掉其他工地的進度。
- 計數達到上限 N 的那一趟必定掉出新機型。仍按原權重從「尚未擁有」的機型中挑選，所以礦坑保底可能先給拆房機；拆房機到手後池中只剩礦用機。
- 只在該工地還有未擁有機型時計數及顯示；全部擁有後不顯示。
- 只保底整台機型；零件掉落已有重複折現，本輪不改。不改單趟機率、權重、工時、金幣、經驗或價格，所以中位數幾乎不變，只截斷長尾。

建議 N = ceil(1／單趟機率)，即平均需要的趟數。模擬（同上口徑）：

| 工地 | N | P50 | P90 | 最差（上限） |
| --- | --- | --- | --- | --- |
| 廢料場 | 34 | 2.8h | 5.0h | 5.7h |
| 窄巷 | 17 | 4.3h | 8.8h | 12.8h |
| 採石場 | 15 | 7.0h | 11.5h | 15.0h |
| 廢鋼場 | 13 | 6.5h | 11.5h | 13.0h |
| 河道 | 10 | 5.3h | 7.5h | 7.5h |
| 山坡 | 10 | 10.0h | 16.0h | 20.0h |
| 深層礦坑 | 9 | 16.0h | 28.0h | 36.0h |

較寬鬆的替代：N = ceil(1.5／機率)（礦坑 N=13，P90 32h、最差 52h），保留更多運氣感。

### 介面

- 工地卡與出發確認：顯示「新機型保底 3／9」。若本趟必定出新機型，顯示「本趟必得新機型」。
- 結果卡：保底觸發時，新機型旁標「保底」；未觸發時顯示更新後的進度。
- 圖鑑來源：派遣限定機型的來源說明加上「連續 N 趟未出必得」。

### 資料與兼容

- 新派遣規則版本 3（=方案 A＋保底）。現存規則 1／2 工作仍按原規則結算，不參與計數，避免升級時有待領工作的人被追溯改變結果。economy.mjs 中 `=== 2` 的判斷改為 `>= 2`，讓規則 3 沿用方案 A 的金幣、磨損與折現。
- 存檔新增 `machinePity: { [siteId]: 次數 }`，schemaVersion 3→4，舊存檔從 0 開始，不追溯補計過去的派遣；非法數值正規化為 0 並限制在 0～N。
- 出發時把該工地當前計數寫入工作快照。由於只有一個派遣槽且計數只在領取時改變，結算結果在出發時已確定，重試／重啟不重抽，與 M1 的固定亂數一致。仍使用既有 11 個亂數，不改 ROLLS_NEEDED。
- 匯出／匯入、重置帶上新欄位；交易持久化成功才回覆，與現有領取相同。

### 驗收案例

1. N−1 趟未出後，第 N 趟必定出新機型，計數歸零；中途自然掉出也歸零。
2. 各工地計數互相獨立；全擁有的工地不計數、不顯示。
3. 規則 1／2 的待領工作升級後按原規則結算，不改計數；規則 3 工作重啟、重試不重抽、不重複計數。
4. 舊存檔遷移為 0；非法值正規化；匯出還原保留計數。
5. 工地卡、出發確認、結果卡、圖鑑來源顯示一致；380px 窄視窗與暗色正常。
6. 平衡報告新增保底後的 P50／P90／最差數據。

### 實現（0.9.0）

規則集中在 `src/shared/pity.mjs`（上限、未擁有機型、正規化、顯示進度）；`rewards.mjs` 結算時判斷自然掉落與保底，`reducer.mjs` 出發時寫入 `job.pity`。economy 的方案 A 判斷改為「規則 ≥ 2」。經濟沙盒仍比較規則 1 與 2，不含保底；平衡報告的指定機型長尾同時列出規則 1 與 3。

### 已確認選擇（2026-10-22）

使用者確認：保底上限 N = ceil(1／單趟機率)；每工地獨立計數；保底觸發時按原權重從未擁有機型挑選。
