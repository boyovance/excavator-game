# 項目計劃書

版本：0.1；日期：2026-10-16；產品基準：0.7.3。

狀態：M0 基礎修復與文檔待使用者驗收；M1 及後續為提案，等待確認後逐區開發。

## 1. 目標與已確認方向

打造以「派遣 → 收穫 → 收集零件／機型 → 搭配 → 挑戰新工地」為核心的桌面養成遊戲。保留桌面陪伴、拖曳和小動作，讓玩家短時間回來也能看到進展。

使用者於 2026-10-16 確認以養成遊戲為重點，並要求開發依照文檔，每完成一個功能或區域提供效果與測試結果，確認後再調整／繼續。

本輪不預設加入帳號、雲端服務、付費抽卡、多人玩法、自動更新或移動端。這些屬於獨立範圍，需另行確認。

## 2. 現況

現有 Electron + TypeScript + Phaser 桌面應用，包含本機 Node 服務、JSON 存檔、車庫、派遣、掉落、機型配件限制、外觀及新手引導。工地時間為 5～120 分鐘，工地／零件數據由源碼資料表管理。

原始工作目錄測試通過，但 Git 忽略規則漏掉必要遊戲資料；本輪修復並增加乾淨檢出驗證。既有功能並非所有桌面交互都已人工驗收，測試通過不替代使用者確認畫面與手感。

## 4. 每個功能區的協作流程

1. 開發前：在設計文檔列出行為、資料變更、介面草圖、驗收案例；需要產品選擇的地方標為「待確認」。
2. 實現：只完成當前確認範圍；出現新限制時先回報具體影響。
3. 技術驗證：規則測試、建置、必要的桌面／存檔測試；記錄未覆蓋項。
4. 交付回饋：說明改了什麼、如何查看效果、操作步驟、預期結果、測試結果及提交號；有畫面改動時附實際截圖或可操作版本。
5. 使用者驗收：狀態停在「待驗收」，不以未回覆等同接受，也不自行開始下一個養成功能區。
6. 調整：將反饋記入本文件，再修改當前區；確認後標記「已驗收」並更新下一區設計。

同一功能區內的必要除錯與測試自主完成，無需逐行請示。新範圍或玩家可感知規則變更要有明確確認。

## 5. 第一個功能區建議：派遣

先改善既有派遣流程，原因是它直接串起收益、掉落、機型與成長。建議保留單一派遣槽，先避免同時引入多隊伍、材料和技能樹。

提案：派遣開始記錄機型和配件快照；結算使用該快照。工作完成後先顯示待領取，玩家查看結果並領取；通知只提示，不代替領取。

這會改變目前場景自動觸發 `claim` 的行為，須先由使用者確認。人工驗收以「選工地 → 確認配置 → 倒數 → 重啟後恢復 → 完成 → 領取 → 確認庫存」為主線。詳見設計文檔 M1。

## 6. 平衡評估方法（M4 提案）

以固定亂數種子模擬各機型／工地組合，分開觀察基礎收益、裝備加成、大豐收、重複掉落折現和維修成本。記錄每小時淨金幣、經驗、未擁有配件獲得率、首台可購機型所需時間、掉落限定機型獲得時間分位數。

先測量現有基準，再提出目標區間供使用者確認；不把暫定數字直接寫進正式遊戲。長工地應有少操作的價值，短工地應有更頻繁回饋，但不能在所有指標上都更優。

## 7. 風險與處理

- 存檔兼容：每次結構變更配套遷移及舊存檔測試，升級前備份。
- 收益失衡：規則和數據集中在 shared 層，先模擬再調數值。
- 狀態機複雜：當 M1 變更派遣時再拆派遣控制器，保持動畫和結算分離。
- 桌面資源佔用：在固定設備測量待機、動畫和隱藏狀態，根據實測結果決定降幀；目前未量測，不承諾效能數字。
- 依賴 override：Windows 打包需驗證，代理網路下載未覆蓋時明確記錄。
- 使用者確認：每次只驗收一區，未確認不推進下一區。
